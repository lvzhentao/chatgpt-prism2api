# 大并发容量方案（CAPACITY-PLAN）

> 目标：**扛 5000+ RPM 全吃下（有多少打进来吃多少）**；实时看到 RPM/TPM；容量随流量自适应伸缩。
> 现状基线：2026-09-19，122 活号。
>
> **用户决策（2026-09-19 已落地配置中心，零代码）**：
> - 每号并发上限 **100**（`account_concurrency`，429 降级值保持 2，热生效）
> - 预热 **全池 122 号**（`prewarm_accounts`，实测首轮 39s 完成，workers 24）
> - **模型出口走服务器直连**（egress direct 保持；仅 auth 登录重登走 arxlabs 代理）
> **扩容决策（2026-09-20 追加）**：材料槽 12→**20**、材料工人 8（`PRISM_MATERIAL_WORKERS`，compose 已传侧车——此前 .env 设 6 但没接线，侧车实际跑默认 4）、sentinel 铸造并发 2→**6**（`PRISM_SENTINEL_CONCURRENCY` 新变量，单路一 node ~150MB）；216 在用号全量 `rpm=80`（94 新号经 `PATCH /api/admin/accounts` 批量补齐——该接口走 Account 落盘路径，无「裸 SQL 被内存 flush 覆盖」问题）。产能账：材料 8 工人×120s/45s≈21 份/2min 养得起 20 槽；sentinel 6 并发×单票 1~2s≈180-360 token/min。身份维度容量 12×80≈960 → **20×80≈1600 RPM**。

## 〇、容量目标与数学（设计依据）

**设计目标（用户拍板）：单号 100 RPM。** 100 号满配 → 理论容量 1 万 RPM；5000 RPM 为半载运行（余量 2 倍）。

```
单号稳态 RPM ≈ 并发上限 ÷ 平均请求时长 × 60
  terra（~20s）：100 并发 → ~300 RPM/号（设计上限自动满足）
  sol  （~60s）：100 并发 → ~100 RPM/号（正好顶格，是瓶颈模型）
5000 RPM ÷ 100 号 = 50 RPM/号 → terra 17 并发、sol 50 并发（半载 ✓）
```

- **本系统侧已就绪**（零代码，配置中心）：并发 100/号（`account_concurrency`，429 降级 2）、全池 122 号预热（39s/轮）、出口直连。
- **上游侧是唯一未知数**：单号 100 RPM 是否触发上游 429/风控/沙箱争抢——以压测为准（§七）。
- **系统层已实测就绪**：容器 fd 524288、出站端口 ~2.8 万；5000 RPM 峰值在飞 ~2500 连接。
- **灾难场景必须防**：5000 RPM 下上游故障 + 无限换号 = 放大 6 倍轰炸——换号上限（M2）优先级最高。

## 一、现有基础盘点（改造起点，不推倒重来）

| 机制 | 现状 | 差距 |
|---|---|---|
| 账号级 RPM | 滑动窗口已有（`pool/account.go` useTimes），**但默认 0=不限** | 裸奔，需默认值 |
| 账号级并发 | inflight 计数 + base/degraded 双档（429 降级）已有 | base 默认值未设 |
| warm-set 预热 | MRU 前 K=16（`prewarm_accounts`），60s sweep，workers 10-24 自适应，失败退避 | **K 固定，不随流量伸缩** |
| 选号 | collectReady 过滤（enabled/RPM/日限/token 本地有效）+ 沙箱温热优先 + inflight 满跳过 | 够用 |
| 观测 | request_logs 落库（tokens/model/status/retry 全有），只能事后 psql 查 | **无实时 RPM/TPM** |
| 入口闸门 | **没有**。超容量时靠无限换号重试内卷（§十遗留） | 本方案核心缺口 |

## 二、核心思想

**容量 = Σ参与账号的配额；闸门按容量放行；热号数随流量伸缩。**

```
观测RPM ──► 目标热号数 = ceil(RPM × 1.5 / 每号安全RPM)   (L3 弹性warm-set)
                │
                ▼
全局并发容量 C = 热号数 × 每号并发                        (账号默认并发)
全局RPM容量  = 热号数 × 每号安全RPM                        (账号默认RPM)
                │
                ▼
入口信号量(cap=C) ──► 排队(≤30s) ──► 429+Retry-After       (L2 闸门)
                │
                ▼
RPM/TPM/排队/水位 实时面板                                 (L1 观测)
```

三句话对应：并发打进来= L2 闸门兜底；看得到 = L1；吃多少伸缩多少 = L3。

## 三、四层设计

### L1 观测层（先做——看不见就没法调）

- **计数器**：`internal/admin/meters.go`，环形桶 1s × 180 个（3 分钟窗口），原子操作。
- **打点**：chat/responses 入口计 `incoming`（带 model/client_key）；完成时计 `served/prompt_tokens/completion_tokens/retry`；闸门处计 `queued/rejected`。
- **暴露**：
  - `GET /api/admin/metrics`（adminAuth）：全局+按模型 RPM/TPM、EWMA、排队深度、热号水位（当前/目标）、429 计数、重试放大系数（上游调用数÷请求数）。
  - dashboard 加"容量卡片"：RPM/TPM 实时数字与 3 分钟 sparkline、水位条（热号 n/target）、排队深度。
- 历史趋势直接用 request_logs（已全量落库），不重复造。

### L2 入口闸门（吃得下）

- server 层信号量：`map[model]chan struct{}`（cap=该模型容量）+ 全局总量信号量（防单模型饿死全部），容量由 L3 每轮广播。
- 排队语义：`select { 拿槽 → 处理; <-time.After(30s) → 429 + Retry-After }`。Retry-After 取 `1 + 队列长度×平均耗时/容量` 的保守值（1~10s）。
- 流式请求已发 SSE 头的（首槽后才发头）不影响；429 在发头之前返回，NewAPI 渠道语义正确（它按 429 走渠道重试/冷却）。
- 现有 `class=server 无限换号重试`（§十遗留）在本层顺带加上限：单请求换号 ≤6 次或累计 120s，先到为准。

### L3 弹性容量（核心："打多少吃多少"）

1. **账号默认配额**（现在是 0=不限）：
   - `rpm = 6`（可配 `PRISM_PER_ACCOUNT_RPM`；校准见 §五）
   - 并发 `base=2, degraded=1`（伪流式整轮占用 13~60s，2 并发≈6RPM 自洽）
   - 生效路径零新代码：collectReady 自动摘除打满的号、总量天花板=热号数×6。
2. **弹性 warm-set**（改 `prewarm_boot.go`）：
   - `targetK = clamp(ceil(observedRPM × 1.5 / 6), 4, 池内Ready号数)`
   - observedRPM 用 L1 的 EWMA（半衰期 60s）；**扩容立即生效**（流量等不起），**缩容延迟 2 轮 sweep**（防抖动，缩容只是停止预热，号自然冷掉，无成本）。
   - 扩容选号顺序：MRU 优先（最近用过的优先复热），其次 Ready 且 token 新的。
3. **容量广播**：prewarm 每轮算出 `C = targetK × 2`，原子写回 L2 信号量（resize 策略：新建 chan 迁移旧槽，简单实现见实施注记）。

### L4 保护与告警

- 水位告警：`热号数/池Ready数 > 90%` 或 `排队拒绝率 > 1%` → 容器日志 WARN + dashboard 红条"容量顶格，建议扩号"。
- 上游故障联动：class=server 失败率突增（如 502 风暴）时自动缩容量并暂停扩容（防把账号池打死）——复用保活退避的失败信号。

## 五、关键假设与校准状态

- ~~每号安全 RPM=6~~ → **压测修正：单号安全 ≈80 RPM**（§七），429 边缘 ~130。
- ~~每号并发=2~~ → **用户拍板 100**（配置中心 `account_concurrency`，已生效）；429 降级 2 保留。
- **排队超时 30s**：NewAPI 端到端口径含排队，超 30s 不如 429 让它换渠道。（M2 待实施）
- **余量系数 1.5**：扩容付 6~10s/号 预热成本，留余量让扩容跑在流量前面。（M3 待实施）

## 六、不做的事（明确出界）

- 不做按 client_key 的公平排队（单租户场景过度设计，FIFO 够）。
- 不做跨进程分布式限流（单实例部署）。
- 不动上游协议层（伪流式整轮返回是上游形态，§四已有结论）。

## 七、单号压测（2026-09-19 已执行）

方法：隔离单号（71-speller-collage，**停机改库**防 dirty-flush 覆盖——运行中裸 SQL 改账号状态会被内存异步落盘覆盖，实测踩过）→ python 并发打 chat（max_tokens=8 极小请求）→ 按 request_logs/日志聚合。

| 档 | 并发 | 成功 RPM | 成功率 | p50/p95 | 上游反应 |
|---|---|---|---|---|---|
| 1 | 10 | **82.4** | 100% | 7.0s / 9.6s | 零错误 |
| 2 | 20 | 128.8（+195×503） | 67.1% | 8.7s / 13.3s | **429×63 → 自动降级并发2 → 选号池空 → 503** |

**结论**：
- 单号**安全持续容量 ≈ 80 RPM**（零错误档）；100 RPM 可达但处于 429 边缘（靠降级+重试吸收）。
- 瓶颈是**上游频控（429/RPM 维度）**，不是本系统：并发 100 未触顶、fd/连接富余、降级与选号联动行为正确（无雪崩、无挂死）。
- 全池推算：122 号 × 80 RPM ≈ **9700 RPM 安全容量**；5000 RPM = 半载运行，**设计成立**。
- 429 出现时 degraded 机制把该号并发降到 2 并摘出轮换——多号大流量下 429 自动均摊，M1 观测要把"429 率/降级号数"做进水位。
